# Relay 项目类型与规则体系

## 设计目标

项目类型不是一个用于展示的标签，而是 Agent 每次进入项目时都会加载的工作约束。旧模型把 WMS、ERP、Web、移动端和后端服务都归入“软件开发”，无法表达领域不变量、验收方法、上线风险和交付物差异。

Relay 采用三层组合模型：

1. **共同治理基线**：适用于所有项目，约束任务、证据、决策、安全、审批、资产和完成定义。
2. **领域分类基线**：描述软件工程、企业系统、数据研究、设计内容或运营交付的共同方法。
3. **项目子类型专项规则**：描述 WMS 库存不变量、ERP 财务期间、MES 生产追溯、小说章节文件等不可弱化要求。

Human 可以补充更严格的项目 Rule，但不能删除、覆盖或弱化系统三层规则。

## 阶段门禁模型

规则不只描述“注意什么”，还必须描述“按什么顺序做”。软件与数字产品统一采用阶段门禁：需求与验收基线 → 体验/界面设计 → 技术选型与架构 → 工程骨架 → 基础模块 → 核心逻辑 → 系统测试 → Docker/部署验证 → 验收、发布与交接。

设计门禁按交付形态触发，而不是按项目类型名称触发。ERP、WMS、MES、CRM、数据项目、自动化、游戏、运营或通用项目只要包含页面、屏幕、HUD、后台、看板、报表布局、设备界面或其他视觉/交互产物，都必须先交付可编辑设计源文件以及 SVG/PDF 审阅件，覆盖关键状态和目标尺寸，并完成评审后才能实现。确实没有视觉交付的纯后端、数据管道、研究或文本项目不虚构页面图，但要提供适合问题的架构、状态、数据流、流程或内容结构设计。

- PM 或具备任务编排权限的 Agent 把阶段转换为任务、评审和真实依赖。
- 执行 Agent 即使看到任务为 `ready`，也必须核对项目 Skill、前置阶段和可访问证据；计划漏配依赖时不得跨阶段开工。
- 同一阶段可以并行边界清晰的任务，后一阶段不得依赖尚未确认的需求、设计或契约。
- 已有项目先审计并复用有效证据，只补缺口，不机械重做；紧急修复需 Human 明确授权并建立补偿任务。

Web 类型进一步固定为：先写需求，画可编辑 SVG，完成 CSR/SSR/SSG、框架、数据、认证、测试与部署选型，搭建可干净启动的工程骨架，开发基础模块，再按用户旅程开发核心逻辑；测试通过后才能完成生产 Docker 构建与部署验证，最后由对应责任人验收交接。

## 分类目录

| 领域 | 项目子类型 |
| --- | --- |
| 软件与数字产品 | 通用软件开发、Web 应用与网站、移动端应用、桌面应用、后端服务与 API、库/SDK/开发工具、游戏开发、IoT 与嵌入式系统 |
| 企业业务系统 | ERP、WMS、CRM、MES、电商与交易平台 |
| 数据、AI 与研究 | 数据分析、数据工程与平台、机器学习与模型系统、研究调研 |
| 设计、内容与知识 | 产品与体验设计、设计系统与品牌、小说创作、专业写作、文档与知识库、市场/品牌/增长内容 |
| 自动化、运营与交付 | 自动化/Agent/集成、运营与持续服务、实施/迁移/上线 |
| 通用项目 | 无法可靠归类时使用的治理基线，不伪造领域结论 |

## 自动识别原则

- Human 明确指定时以 Human 选择为准。
- 自动识别同时读取项目名称、说明和导入文件结构。
- 业务领域关键词的权重高于通用工程清单。例如“WMS + 波次 + PDA + `package.json`”应识别为 WMS，而不是普通软件开发。
- 明确框架或领域文件可作为强证据，例如 `pubspec.yaml`、`project.godot`、`dbt_project.yml`。
- 置信度不足时回退到通用项目，不以猜测生成看似专业但错误的规则。
- 识别结果保留来源、置信度和命中证据，供 Human 审阅和修正。

## 专项规则示例

### WMS

必须覆盖收货、质检、上架、补货、波次、拣选、复核、包装、出库、盘点；定义在库、可用、分配、冻结、残损和在途库存不变量；处理批次、序列号、效期、单位换算、并发分配、重复扫码和设备离线；与 ERP/OMS/TMS 集成必须具备幂等、死信、重放和日终对账。

### ERP

必须先建立组织、科目、期间、币种、税、主数据和单据状态；财务过账遵守借贷平衡；关账、反关账、冲销和调整可审计；上线前完成期初、未结单、库存和往来余额迁移与对账。

### 游戏开发

需求以核心循环、输入、反馈、失败/胜利条件和关卡节奏表达；可玩性必须通过真实运行验证；缺陷需要最小复现项目、平台/引擎版本和回归证据；资产管线、性能预算、存档兼容与多设备输入属于交付的一部分。

### 小说创作

先建立主题、受众、叙事视角、人物弧、世界规则和章节大纲；每章独立文件；维护时间线、角色状态、伏笔和设定一致性；阶段性审阅结构、节奏、因果和语言，而不是只检查字数。

## 参考项目与吸收的实践

本体系没有复制第三方文本，而是从成熟开源项目的工程组织和贡献要求中提炼原则：

- [ERPNext](https://github.com/frappe/erpnext)：财务、销售、采购、库存和制造等业务领域边界。
- [OpenWMS](https://github.com/openwms/org.openwms)：库存服务、仓储作业、设备/MFC/PLC 集成和领域服务拆分。
- [Godot](https://github.com/godotengine/godot)：最小复现、版本验证、跨平台问题和正式评审。
- [Flutter](https://github.com/flutter/flutter)：回归测试、平台质量、问题复现和发布稳定性。
- [Next.js](https://github.com/vercel/next.js)：核心模块分层、文档、测试和兼容性治理。
- [dbt Core](https://github.com/dbt-labs/dbt-core)：数据变换环境、测试、CI、变更记录与评审。
- [Cookiecutter Data Science](https://github.com/drivendataorg/cookiecutter-data-science)：原始数据、处理过程、模型、报告和环境的可复现分层。
- [novelWriter](https://github.com/vkbo/novelWriter)：长篇作品的小文件组织、章节结构和元数据管理。
- [Medusa](https://github.com/medusajs/medusa) 与 [Saleor](https://github.com/saleor/saleor)：订单、库存、支付、迁移和交易系统测试。
- [Architecture Decision Records](https://github.com/joelparkerhenderson/architecture-decision-record)：重要决策的背景、候选方案、取舍和后果记录。

## 扩展新类型

新增类型时必须同时完成：

1. 定义稳定的类型 key、中文名称、领域分类和适用边界。
2. 明确该领域独有的不变量、失败模式、验收证据和上线风险，不能只改标题。
3. 在类型目录中组合共同基线、领域基线和专项规则。
4. 增加描述/文件证据与权重，确保专业类型优先于通用类型。
5. 扩展数据库约束、前端分类展示、API 类型和回归测试。
6. 用真实项目描述验证正例、反例和相邻类型冲突。
